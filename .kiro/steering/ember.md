# Ember — project steering file

## What we're building

Ember v2 is a chest-strap device that estimates **core body temperature** from
heart rate, shows a **calibrated 90 % range** (conformal intervals, not the Kalman
variance), and says **Cannot estimate** (shown as *Paused* in the app) when its
signals disagree.

Hardware v5: one analog pulse sensor and two skin thermistors on the chest, a third
thermistor in the air outside the strap, a GY-521 IMU for motion, all on an ESP32-S3
powered by a USB power bank. **No SHT40 (so no humidity), no second pulse sensor, no
Polar strap, no OLED, no buzzer.** The device does all the estimation and sends one
20-byte frame a second over Bluetooth LE to a web app in Chrome. Wiring:
`ember/wiring_v5.html`.

Hackathon demo (DS+X, Boston University, Oct 24–25 2026): one device, one wearer.
Not a medical device. Consenting adults only.

Status and next steps live in `ember/TODO.md` (Phases 1–7). Phases 1–3 are done.
Phase 4 (Web Bluetooth hookup) is done in software; it still needs a check on the real
device. Phase 5 (demo safety net) is next.

## Hardware (v5)

| Part | Pin | Notes |
|---|---|---|
| Pulse sensor | GPIO4 | analog |
| Air thermistor C (10k NTC divider, R3) | GPIO5 | hangs outside the strap; display only |
| Skin thermistor A / B (10k NTC divider, R1 / R2) | GPIO6 / GPIO7 | analog |
| Battery sense, held at 0 V by R4 | GPIO8 | reads "no battery": battery byte is always 255 |
| IMU GY-521 (0x68) | SDA GPIO17, SCL GPIO18 | I²C, 100 kHz |

On the demo board, all three dividers are built upside down (thermistor on the
3V3 side, the 10k to GND). `NTC_A_ON_TOP`, `NTC_B_ON_TOP`, `NTC_C_ON_TOP` (all 1)
in `ember.ino` flip the maths via `ntcNodeMv()`; set one to 0 if that divider is
rewired to match the diagram, then rerun `CAL`.

Power is USB-C from a power bank (or the laptop). Every analog input must stay on
ADC1 (GPIO1–10): ADC2 returns garbage while BLE runs.

## Bluetooth contract

Full spec: `docs/APP_INTERFACE.md`. Reference decoder: `decode()` in `tools/ember_ble.py`.

- Name `Ember`. Service `e3b10001-5a2f-4c8e-9b7d-656d62657200`; live frame `…0002`
  (notify, 20 bytes, 1 Hz); command `…0003` (write ASCII: `BASELINE`, `START`,
  `STOP`, `CAL`, `STATUS`, `ID`).
- Frame is little-endian: core °C×100 (int16, −32768 = none), ± °C×50 (255 = none),
  state byte (low nibble 0 OK / 1 CAUTION / 2 REFUSE; bit 4 baseline running; bit 5
  logging), 16-bit flags, then heart rate, skin, air temperature, activity. Bytes
  14, 15, 18 and 19 are reserved (2.1's humidity, headroom and per-sensor heart
  rates) and always sent as "none".
- On REFUSE the device sends the core and ± as "none". Never fill the gap with an
  older value.
- From 38.0 °C up the device never refuses: the worst state is CAUTION, and the
  frame keeps the number and a ± that widens while the pulse is lost.
- `seq` only counts while connected; timestamp frames on arrival.
- The frame, flags and reason order must stay identical in `ember_core.h`,
  `ember_ble.py`, `APP_INTERFACE.md` and the webapp (`frame.js`). Change them together.

Serial (bench only): `START` streams a 19-column CSV at 1 Hz:

```
ms,hr,sqi,hr_q,step_hz,act_g,skinA,skinB,skin,skin_q,air_c,vbat,ct_est,ct_lo,ct_hi,kalman_half,filter_step,state,flags
```

Flags print as `0x%04X`, missing values as `nan`. Unlike the BLE frame, the CSV
always carries `ct_est`, so the app must withhold the number itself when `state`
is 2.

## Thresholds and statuses

| Status | Estimate | Colour |
|---|---|---|
| OK | below 38.0 °C | light blue `#EAF2FB` / `#0B5CAD` |
| Watch | 38.0 °C and up | solid amber `#FFB020` |
| Act now | 38.5 °C and up | solid red `#B42318` |
| Paused | no number (REFUSE) | slate `#3A4B5C` |

- 38.5 is the ACGIH work limit; 38.0 is the evaluation's "elevated" cutoff and the
  WHO limit. Watch carries the safety load because the estimate lags true core.
- The firmware only knows 38.0 (`CT_WATCH_C`). Both thresholds live in `THRESHOLDS`
  in `datastore.js`; UI text reads them through `fmtC()`. Never hardcode threshold
  numbers in UI text.
- Tags: **Low confidence** when the firmware state is CAUTION, with the reason
  beside it. **Setting up** while the baseline runs (state bit 4, 5 minutes).
- `BASELINE` restarts the filter from a resting value and hides the number for a
  minute. Offer it only during setup. The firmware ignores it at 38.0 or above and
  cancels a baseline that ends there.
- **Never Paused at 38.0 °C or above.** Show the number with Low confidence.
- Decide Paused from the state or a blank number, never from a flag alone: at
  38.0 and up, "no trustworthy heart rate" (0x0008) arrives as CAUTION with a number.

### What the firmware flags mean

- REFUSE (below 38.0 only): `STALE_HR` 0x0008, or both doubts:
  `MOTIONLESS_TACHY` 0x0001 and `COOL_SKIN` 0x0004.
  - The stillness doubt (0x0001) needs an IMU, waits 10 min after the wearer last
    moved, and never fires at 38.0 or above.
  - The skin doubt (0x0004) only fires after `CAL`. On an uncalibrated unit
    "Cannot estimate" can't come from doubts, so `CAL` is required before
    recording or presenting.
- CAUTION: one doubt, or `NO_BASELINE` 0x0020, `BASELINE_RUNNING` 0x8000,
  `CADENCE_LOCK` 0x0040.
- Info only, never change the state: `SKIN_DISAGREE`, `SKIN_SINGLE`, `NO_AIR`
  0x1000 (air thermistor not reading), `LOW_BATT`, `NOT_CALIBRATED`.
- Reserved, never set: 0x0010 (was WIDE_INTERVAL in 2.0), 0x0100 and 0x0200 (2.1's
  two-sensor flags): never reuse. 0x0002 and 0x0080 (2.1's humidity-based "no
  thermal load" and "struggling to cool down") stay free for an air-temperature
  version once its thresholds are tested.
- One pulse sensor: nothing cross-checks the heart rate. Only the signal-quality
  gate and the cadence jump test protect it.
- `CAL` has no reference sensor: it makes the three thermistors agree at room
  temperature (about ±0.6 °C absolute). A board calibrated against the SHT40
  under 2.1 keeps its skin calibration and only calibrates the air bead.
- One reason per state: the first set flag in `flagReason()` order (`ember_core.h`).

## Wording

- The product is **EMB.R** in all UI text. The BLE name (`Ember`), code, file
  names and docs stay "Ember". The demo wearer is Charles Nelson (`WEARER_NAME`).
- "Estimated core temperature", not "your temperature". Thresholds are
  recommendations, not diagnoses.
- "This is an estimate, not a medical reading." is always visible in the Personal
  view footer.
- Calm, direct copy. No alarm language until Act now.
- Talk about heating up and cooling down, never sweat or evaporation. Never show kPa.
  (2.1's 0x0080 line, "Your body is struggling to cool down.", is gone with the
  SHT40; reuse the wording if an air-based version comes back.)
- Paused reasons in plain words:
  - 0x0008: "Pulse signal lost. Press the sensors flat against your skin."
    (but "Starting…" while no number has arrived yet after connect or baseline)
  - 0x0001: "Your heart rate is up, but your body doesn't look like it's heating up."
  - otherwise: "Your sensors disagree right now."
- Forecast is a range ("about 10–25 min"), capped at 30 min, shown only when
  rising. Never a countdown. Trend as a rate ("↑ 0.3° / 10 min").
- A missing ± shows "—", never a made-up number.
- Say "Demo" when simulating, not "Live".

## Three views

**Personal (the live demo).** Status block first (estimate, ±, status, tag), then
"Your plan" (one action, forecast, next break, water, "Start my break", "I drank"),
then the 30-minute chart (core with its range, and skin), heart rate, motion, and
one air line: the device's air temperature ("Air near you") and the weather if it
loaded. "How sure is Ember?" opens the real coverage numbers. The
footer says what is shared and carries the disclaimer.

**Coach (static example)**, labelled "Example team · 12 players". Player cards
sorted by risk, counts per status, "Do this now", weather, buttons that answer with
a toast. Statuses come from `THRESHOLDS`.

**Supervisor (static example)**, labelled "Example crew". **No body data at all**:
only events (overheating alert, rest break taken, estimate unavailable), "I checked
in" / "Call worker", and a "Who sees what" card. Optional later: the live wearer's
Act now as one event, with no temperature.

Design: Inter font, ink `#0B1B2B`, status colours above; reference in
`design-export/`. Break and water schedule are placeholders (20 min on / 5 off,
250 ml every 15 min) until a cited table is chosen.

## Privacy and security — non-negotiable

- **Zero persistence.** No localStorage, IndexedDB, cookies or server writes. All
  state lives in memory and dies on page close.
- **No raw biometrics in the Supervisor view.** Event types only, never heart rate,
  skin temp or core temp.
- No login, accounts or tracking. One hardcoded device.
- Data flows device → `datastore.js` → views. The only write back is a command to
  the device (`BASELINE`).
- Outbound requests: Open-Meteo (latitude/longitude only) and Google Fonts (Inter).
  Nothing else.

## Tech stack (webapp)

- Vanilla JS ES modules, HTML, CSS. No build step, no framework. Serve it locally
  (modules don't load from `file://`), e.g. `python3 -m http.server` in `webapp/`.
- Charts are plain SVG drawn in the view. No chart library.
- Web Bluetooth (Chrome) for the device; Web Serial kept for the bench.
- Open-Meteo for weather, no key.

## Firmware conventions (don't break these)

- All arithmetic lives in `ember_core.h` with a unit test in `tests/test_core.cpp`.
  `ember.ino` is hardware and wiring.
- ECTemp coefficients B2=-4.5714, B1=384.4286, B0=-7887.1. Never retype them; they
  match `analysis/ectemp.py`, and `coefficientsSane()` halts the board at boot if
  they are wrong.
- The filter steps once a minute on the minute-mean heart rate, the cadence the
  calibration was built at. Don't shorten it.
- The displayed ± is the conformal half-width from `conformal_table.h`, plus coast
  inflation. `kalman_half` goes to the serial CSV only and is **never displayed**:
  it demonstrates the uncalibrated interval's failure (34 % coverage of a "90 %" range).
- `conformal_table.h` and `conformal_table.js` are generated together; don't
  hand-edit them:
  `cd analysis && python3 export_firmware_table.py --data "Prospie dataset_open access V3.xlsx" --out ../firmware/ember/conformal_table.h --js-out ../webapp/src/lib/conformal_table.js`
- **Do not remove the refusal logic.** It is the point of the project. It refuses
  only on signal doubts, never because the range is wide, and never at 38.0 °C or above.
- Bump `FW_VERSION` in `ember.ino` when behaviour changes (2.2.2 now), so `ID` shows
  which build is flashed, and update the expected `ID` output in the build guide.

## Checks to run

From `ember/`:

- Firmware unit tests (all must pass; the count grows as fixes land):
  `g++ -std=c++17 -O2 -Wall -Wextra -Ifirmware/ember tests/test_core.cpp -o /tmp/test_core && /tmp/test_core`
- Sketch type-check against the stubs (not a real ESP32 compile; that needs the
  Arduino IDE with the esp32 core):
  `g++ -std=c++17 -fsyntax-only -Itests/stubs -Ifirmware/ember -x c++ firmware/ember/ember.ino`
- Decoder, including the reason order against `ember_core.h`:
  `python3 tools/ember_ble.py --selftest`
- Webapp data path (frame decoder against the self-test frames and `ember_core.h`,
  bench CSV, datastore rules) and link layer (fake Web Bluetooth device, ~5 s):
  `node --test tests/test_frame.mjs tests/test_link.mjs`
- Webapp: `node --check` every edited module, then test in a browser at 390 px and
  1280 px wide with the simulation running.
- Build guide: edit `guide/phases.html` or `guide/template.html`, run
  `python3 guide/build_guide.py` (rewrites `ember_build_guide.html` and
  `open_me.html`), then mirror the change in `docs/BUILD_GUIDE.md`.

## Demo setup

- Presenting laptop: Chrome, Bluetooth on, webapp served locally. Personal view on
  the projector, live over Bluetooth. Coach and Supervisor on other screens with
  `?view=coach` / `?view=supervisor` (static examples).
- Demo unit: `ID` shows v2.2.2 and "thermistor calibration: yes" (run `CAL` first).
- Demo bout: 5 min `BASELINE`, 12 min hard work, 10 min recovery. Pick work whose
  step rate is far from the heart rate (step-ups, cycling), not running.
- Don't reload the page during the demo: after a reload, Web Bluetooth needs a new
  click in the device chooser.
- If the device fails on stage, replay a recorded session in the same app (Phase 5).

## What not to do

- No backend, server or database.
- Don't store biometric data anywhere.
- Don't display the Kalman interval as a confidence interval.
- Don't remove Cannot estimate / Paused, or the never-hide-at-38.0 rule.
- Don't show heart rate, skin temp or core temp in the Supervisor view.
- Don't hardcode threshold numbers in UI text.
- Don't reuse flag bits 0x0010, 0x0100 or 0x0200.
- Don't edit `docs/BOM.md` (the frozen v1 list; the v2 parts list is in the build guide).
